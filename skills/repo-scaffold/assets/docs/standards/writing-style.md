# 글쓰기 규칙

저장소의 글은 코드와 함께 오래 남고, 사람과 에이전트가 함께 읽는다. 그래서 누가 쓰든 같은 언어와 형식으로 쓰고, 코드가 바뀌어도 틀리지 않게 쓴다.
이 규칙은 문서, 코드 주석, 커밋 메시지, 이슈와 PR, 에이전트에게 주는 프롬프트, 작업 결과를 알리는 답변에 적용한다.

## 언어

| 대상 | 언어 | 비고 |
| --- | --- | --- |
| 문서, 코드 주석 | 한국어 | |
| 커밋 메시지, 이슈, PR | 한국어 | |
| 프롬프트, 답변 | 한국어 | |
| 스크립트 출력 | 영어 | 로그를 검색하기 쉽고, 콘솔 인코딩에 따라 한글이 깨지는 일이 없다 |
| 식별자, 명령, 경로, 설정 키 | 원어 | 바꿔 쓰면 검색하거나 복사해서 실행할 수 없다 |

번역어가 정착된 용어는 번역어로 쓰고(저장소, 병합, 배포), 그렇지 않은 용어는 원어로 쓴다(hook, front matter).
억지로 만든 번역어는 아무도 그 말로 검색하지 않는다.

## 구성

- 첫 문단에 결론을 쓴다. 읽는 사람은 첫 문단을 보고 나머지를 읽을지 정한다.
- 문서는 front matter의 `title`과 같은 H1 하나로 시작하고, 바로 아래에 문서가 다루는 범위를 한두 문장으로 쓴다. 절은 H2로 나눈다.
- 제목, 표 머리글, 상태 이름, 선택지는 짧은 명사구로 쓴다. 파일과 이미지 같은 산출물의 제목도 같다.
  `캐시를 언제 지우는가`보다 `캐시 무효화 시점`이 낫다. 명사구로 줄이면 뜻이 달라지는 제목만 영어 절로 쓴다(`Fail fast on bad input`).
- 표는 값을 비교하는 데 쓴다. 칸 하나에는 이름, 링크, 날짜, 숫자, 정해진 선택지 중 하나만 넣는다.
  문장은 `설명` 열과 `비고` 열에만 쓰고, `비고`는 마지막 열에 둔다. 영어 문서에서는 `Description`과 `Notes`를 쓴다.
- 구조가 글보다 잘 드러나면 표, 목록, Mermaid, ASCII 다이어그램을 쓴다.
- 관련 문서와 외부 자료는 마지막 절 `같이 보기`에 모은다. 영어 문서에서는 `See Also`를 쓴다.
  `참고`나 `References` 같은 다른 이름을 쓰지 않아야 사람과 에이전트가 같은 절을 같은 이름으로 찾는다.

## 내용

- 정확성이 먼저다. **쉽게 쓰려고 틀린 말을 하지 않는다.**
- 어떻게 하는지와 함께 왜 그렇게 하는지를 쓴다. 이유를 알아야 규칙에 없는 상황에서도 같은 판단을 한다.
- 어려운 개념은 구체적인 예와 단계로 풀고, 도움이 되면 일상적인 비유를 든다.
  설명을 돕는 비유는 쓰되, 낱말 하나를 비유로 바꾸지는 않는다([문장과 낱말](#문장과-낱말)).

## 낡지 않는 글

저장소의 글은 코드가 바뀐 뒤에도 그대로 남는다. 코드가 바뀔 때 함께 고칠 글이 적도록 쓴다.

- 같은 내용을 두 곳에 쓰지 않는다. 한 곳에 쓰고 다른 곳에서는 링크한다.
  사본이 생기면 한쪽만 고쳐지고, 에이전트는 먼저 읽은 쪽을 믿는다.
- 바뀔 수 있는 값, 개수, 상태는 옮겨 적지 않고, 그 값을 정의하는 곳을 가리킨다.
  - `Node 20 이상이 필요하다` → `` 필요한 Node 버전은 `package.json`의 `engines`에 있다 ``
  - `규칙 문서는 다섯 개다` → `규칙 문서 목록은 [색인](../index.md)에 있다`
- 외부 개념(도구, 규격, 라이브러리)을 설명하는 문서에는 이 저장소의 상태(디렉터리 이름, 설정, 도입 범위)를 쓰지 않는다.
  저장소 구조가 바뀌었을 때 고쳐야 하는 문단이 상태다. 상태는 저장소 자체를 다루는 문서(`README.md`, `AGENTS.md`)에 쓰고 링크한다.
- 문서와 주석에는 지금의 사실만 쓴다. `이제`, `기존에는`, `이번에 추가한`은 읽는 사람이 알 수 없는 시점을 가리킨다.
  무엇을 왜 바꿨는지는 커밋 메시지, PR, 결정 기록에 쓴다. Git이 그 기록을 코드와 함께 보관한다.
- `scripts/doc-index.sh`가 만드는 색인은 문서의 `title`과 `description`을 옮겨 적는다. 도구가 다시 만들므로 낡지 않는다.
  결정 기록의 맥락과 확인 방법에는 결정할 때의 값을 그대로 둔다. 그 값이 결정의 근거이기 때문이다.

## 어조

답이 아닌 문장은 읽는 시간만 늘린다.

- 묻거나 맡긴 일에 답하는 내용만 쓴다.
- 인사, 질문 되풀이, 할 일 예고, 얼버무림, 면책 문구, 형식적인 경고, 잡담을 쓰지 않는다. 답변, 문서, 커밋 메시지, PR이 모두 같다.
- 되돌릴 수 없는 결과는 경고 문구가 아니라 사실로 쓴다. `주의하세요` → `이 명령은 원격 브랜치를 덮어쓴다`
- `정말`, `매우`, `핵심적인` 같은 강조어 대신 사실과 이유를 쓴다.
- 요청한 사람의 말투를 따라 하지 않는다. 서브에이전트에게 쓰는 프롬프트도 이 규칙을 따른다.

## 문장과 낱말

한국어는 조사와 어미가 낱말 사이의 관계를 정한다. 그것을 빼면 읽는 사람이 뜻을 짐작해야 한다.

- 문장은 평서형 `~한다`로 끝낸다. 지시도 `~한다`로 쓰고 `~하세요`를 쓰지 않는다. 사용자에게 하는 답변은 `~합니다`로 끝내도 된다.
- 문장을 명사(`확인 필요`)나 연결어미(`~하고`, `~하는데`)로 끝내지 않는다. 제목, 표의 칸, 목록 항목은 명사구로 끝내도 된다.
- 한 문장에는 한 가지 내용만 쓴다.
- 주어, 목적어, 조건처럼 뜻을 담은 성분을 생략하지 않는다. 생략한 성분은 쓴 사람만 안다.
  `그러면 오류가 난다.` → `설정 파일이 없으면 서버가 시작할 때 오류가 난다.`
- 조사와 어미를 빼고 명사만 잇지 않는다. `배포 전 설정 확인 필요.` → `배포하기 전에 설정을 확인한다.`
- `의`를 잇달아 쓰지 않는다. `요청의 헤더의 값의 검증` → `요청 헤더에 담긴 값을 검증한다`
- 뜻이 분명한 낱말을 고르고, 낱말 사이의 관계는 조사와 어미로 드러낸다.
  `캐시 무효화 시점 판단 로직 오류 시` → `캐시를 비울 시점을 판단하는 로직에 오류가 생기면`
- 일반적인 낱말 자리에 비유를 쓰지 않는다. `값을 박는다` → `값을 명시한다`, `프로세스가 죽는다` → `프로세스가 종료된다`.
  그 분야에서 용어로 굳은 말은 그대로 쓴다.
- 쉬운 말을 쓴다. 전문 용어와 약어는 필요할 때만 쓰고, 처음 나올 때 풀어 쓴다.
- 한 개념에는 한 이름만 쓴다. `저장소`와 `레포`를 섞어 쓰면 읽는 사람은 둘을 다른 것으로 이해한다.

## 기호와 표기

표기를 하나로 정하면 검색과 diff가 단순해진다.

- 굵게는 놓치면 안 되는 말에만 쓴다. 굵게가 많으면 어느 것도 눈에 띄지 않는다.
- `·`, `〃`, `—`, `–`를 쓰지 않는다. 이 기호들은 앞뒤 말의 관계를 감춘다.
  나열은 쉼표나 `와`, `과`로 하고, 문장 사이의 관계는 콜론이나 접속사로 나타낸다.
- `--`는 명령줄 옵션에만 쓴다. 본문에 쓰면 옵션과 구별되지 않는다.
- 경로, 명령, 설정 키, 값, 식별자는 백틱으로 감싼다.
- 조사는 영문, 숫자, 백틱 뒤에서도 띄우지 않고 붙인다(`AGENTS.md를`).
- 저장소 파일은 저장소 루트 기준 경로로 쓴다(`scripts/doc-index.sh`).
  홈 디렉터리 아래는 `~/`로, Windows에만 있는 위치는 `%APPDATA%`나 `%LOCALAPPDATA%`로 시작한다.
- 운영체제는 Windows, macOS, Linux 순서로 나열한다.
- 날짜는 `YYYY-MM-DD`로, 시각은 시간대 오프셋을 붙인 ISO 8601(`2026-11-08T09:00:00+09:00`)로 쓴다.
- 목록 기호는 `-`를 쓴다. `scripts/doc-index.sh`가 만드는 `index.md`만 OKF 형식에 따라 `*`를 쓴다.

## 링크

- 저장소 안의 문서는 상대 경로로 링크한다.
  OKF는 `/`로 시작하는 경로도 허용하지만, GitHub는 그 경로를 저장소 루트에서 찾으므로 `docs/` 안의 링크가 깨진다.
- 절을 가리킬 때는 절 제목을 링크 텍스트로 쓴다(`[링크](writing-style.md#링크)`). 제목이 바뀌어 anchor가 깨져도 링크 텍스트로 절을 찾을 수 있다.
- 외부 링크는 `[이름](URL)`로 쓴다. 이름이 있어야 열어 보기 전에 무엇인지 안다.

## 코드 주석과 커밋 메시지

- 주석에는 코드만 보고는 알 수 없는 이유를 쓴다. 코드가 하는 일을 되풀이하지 않는다.
- 우회 코드의 주석에는 증상과 원인을 쓴다. 원인이 사라지면 우회 코드를 지워도 되는지 그 주석으로 판단한다.
  `# Windows는 실행 비트를 기록하지 못한다. 그대로 두면 다른 운영체제에서 hook이 실행되지 않으므로 git 인덱스에 직접 기록한다.`
- 커밋 메시지의 제목에는 무엇을 바꿨는지 한 줄로 쓰고, 본문에는 왜 바꿨는지 쓴다. 무엇을 바꿨는지는 diff가 보여 준다.

## 규칙 문서

front matter의 `type`이 `Standard`인 문서는 다음을 지킨다.

- 규칙마다 이유를 쓴다. 이유가 길면 [결정 기록](decisions.md)으로 옮기고 링크한다.
- 규칙과 함께 바꿔야 하는 파일은 `함께 고칠 곳` 절에 표로 쓴다.
- 규칙을 어디서 확인하는지(CI, 스크립트, 리뷰)는 `검사` 절에 쓴다. `검사` 다음에는 `같이 보기`만 온다.

## 검사

자동 검사는 없다. 리뷰에서 확인한다.
