# 글쓰기 규칙

문서, 코드 주석, 커밋 메시지, 이슈와 PR, 에이전트에게 주는 프롬프트, 작업 결과를 알리는 답변에 적용하는 규칙이다.

## 언어

| 대상 | 언어 | 비고 |
| --- | --- | --- |
| 문서, 코드 주석, 커밋 메시지, 이슈, PR, 프롬프트, 답변 | 한국어 | |
| 스크립트 출력 | 영어 | 로그 검색이 쉽고 콘솔 인코딩에 따른 한글 깨짐 없음 |
| 식별자, 명령, 경로, 설정 키 | 원어 | 바꿔 쓰면 검색과 복사 실행 불가 |

번역어가 정착된 용어는 번역어로 쓰고(저장소, 병합, 배포), 그렇지 않은 용어는 원어로 쓴다(hook, front matter).

## 문체

| 대상 | 서술 문장의 끝 |
| --- | --- |
| 에이전트가 따르는 지침(`AGENTS.md`, 스킬, `docs/` 아래 문서, 프롬프트), 코드 주석 | `~한다` |
| 사람에게 건네는 글(`README.md`, `SECURITY.md`, 커밋 메시지 본문, 이슈와 PR의 본문과 댓글, 답변) | `~합니다` |

- 지시도 같은 문체로 쓰고 `~하세요`를 쓰지 않는다.
- 제목, 헤딩, 표 머리글, 상태 이름은 명사구로 쓴다. `왜 이렇게 됐나` → `발생 원인`
- 커밋, 이슈, PR의 한국어 제목은 명사나 `~함`, `~음` 같은 명사형 어미로 끝낸다. 제목이 식별자, 숫자, 영어로 끝나면 적용하지 않는다.
- 목록 항목, 표의 칸, `항목: 값`의 값은 개조식으로 쓰고 명사나 `~함`, `~음`으로 끝낸다. `관리 상태: 마지막 커밋은 2026-11-13이다.` → `관리 상태: 2026-11-13 마지막 커밋`
- `~한다`로 쓰는 지침에서는 목록 항목을 `~한다` 문장으로 써도 된다.
- 개조식 항목에는 [문장과 낱말](#문장과-낱말)의 조사와 어미 규칙을 적용하지 않는다.

## 내용 선별

- 문장과 항목에는 그 자리에서 답해야 하는 내용만 쓰고, 묻지 않은 부가 설명을 덧붙이지 않는다. `AGENTS.md를 추가했다. AGENTS.md는 에이전트가 읽는 파일이다.` → `AGENTS.md를 추가했다.`
- 이유와 배경은 읽는 사람이 판단하거나 행동하는 데 필요할 때만 쓴다. `--dry-run으로 먼저 실행한다. 안전하게 작업하기 위해서다.` → `--dry-run으로 먼저 실행한다.`
- 한 문서 안에서 같은 내용을 여러 번 쓰지 않고, 한 개념을 여러 표현으로 바꿔 말하지 않는다. `설정이 적용되지 않았다. 즉, 변경 사항이 반영되지 않은 것이다.` → `설정이 적용되지 않았다.`
- 쉽게 쓰려고 틀린 말을 하지 않는다.
- 인사, 질문 되풀이, 할 일 예고, 얼버무림, 면책 문구, 형식적인 경고, 잡담, 강조어(`정말`, `매우`, `핵심적인`)를 쓰지 않는다.
- 되돌릴 수 없는 결과는 경고 문구 대신 사실로 쓴다. `주의하세요` → `이 명령은 원격 브랜치를 덮어쓴다`
- 요청한 사람의 말투를 따라 하지 않는다. 서브에이전트에게 주는 프롬프트와 서브에이전트의 결과를 전하는 글도 이 규칙을 따른다.

## 구성

- 첫 문단에 결론을 쓴다.
- 문서는 front matter의 `title`과 같은 H1 하나로 시작하고, 바로 아래에 문서가 다루는 범위를 한두 문장으로 쓴다. 절은 H2로 나눈다.
- 표는 값을 비교하는 데 쓴다. 칸 하나에는 이름, 링크, 날짜, 숫자, 정해진 선택지 중 하나만 넣고, 설명은 `설명` 열이나 마지막 `비고` 열에 쓴다. 영어 문서에서는 `Description`과 `Notes`를 쓴다.
- 구조가 글보다 잘 드러나면 표, 목록, Mermaid, ASCII 다이어그램을 쓴다.
- 어려운 개념은 구체적인 예와 단계로 푼다.
- 관련 문서와 외부 자료는 마지막 절 `같이 보기`에 모은다. 영어 문서에서는 `See Also`를 쓴다. 절 이름이 하나여야 사람과 에이전트가 같은 절을 같은 이름으로 찾는다.

## 낡지 않는 글

코드가 바뀔 때 함께 고칠 글이 적도록 쓴다.

- 같은 내용을 두 곳에 쓰지 않는다. 한 곳에 쓰고 다른 곳에서는 링크한다. 사본이 생기면 한쪽만 고쳐지고, 에이전트는 먼저 읽은 쪽을 따른다.
- 바뀔 수 있는 값, 개수, 상태는 옮겨 적지 않고 그 값을 정의하는 곳을 가리킨다.
  - `Node 20 이상이 필요하다` → `` 필요한 Node 버전은 `package.json`의 `engines`에 있다 ``
  - `규칙 문서는 다섯 개다` → `규칙 문서 목록은 [색인](../index.md)에 있다`
- 외부 개념(도구, 규격, 라이브러리)을 설명하는 문서에는 이 저장소의 상태(디렉터리 이름, 설정, 도입 범위)를 쓰지 않는다. 상태는 저장소 자체를 다루는 문서(`README.md`, `AGENTS.md`)에 쓰고 링크한다.
- 문서와 주석에는 지금의 사실만 쓰고, 무엇을 왜 바꿨는지는 커밋 메시지와 PR에만 쓴다. 문서와 주석에 남긴 변경 이력은 코드가 다시 바뀌어도 고쳐지지 않아 사실과 어긋나고, 에이전트는 그 이력을 지금의 지시로 읽는다.
- `이제`, `기존에는`, `이번에 추가한`처럼 시점을 가리키는 말을 쓰지 않는다.
- 두 가지는 옮겨 적어도 된다. `scripts/doc-index.sh`가 만드는 색인은 도구가 다시 만들므로 문서의 `title`과 `description`을 옮겨 적는다. 결정 기록의 맥락과 확인 방법에는 결정할 때의 값을 그대로 둔다.

## 문장과 낱말

한국어는 조사와 어미가 낱말 사이의 관계를 정한다.

- 문장을 명사(`확인 필요`)나 연결어미(`~하고`, `~하는데`)로 끝내지 않는다. 개조식 항목은 예외다.
- 한 문장에는 한 가지 내용만 쓴다.
- 주어, 목적어, 조건처럼 뜻을 담은 성분을 생략하지 않는다. `그러면 오류가 난다.` → `설정 파일이 없으면 서버가 시작할 때 오류가 난다.`
- 조사와 어미를 빼고 명사만 잇지 않는다. `배포 전 설정 확인 필요.` → `배포하기 전에 설정을 확인한다.`
- `의`를 잇달아 쓰지 않고 풀어 쓴다. `사본의 문구는 작업의 상황을` → `사본에 적힌 문구는 작업이 진행되는 상황을`
- 뜻이 구체적인 낱말을 고르고, 낱말 사이의 관계는 조사와 어미로 드러낸다. `캐시 무효화 시점 판단 로직 오류 시` → `캐시를 비울 시점을 판단하는 로직에 오류가 생기면`
- 일반적인 낱말 자리에 비유를 쓰지 않는다. `값을 박는다` → `값을 명시한다`, `프로세스가 죽는다` → `프로세스가 종료된다`. 그 분야에서 관용 표현으로 굳은 말은 그대로 쓴다.
- 전문 용어와 약어는 필요할 때만 쓰고, 처음 나올 때 풀어 쓴다.
- 한 개념에는 한 이름만 쓴다. `저장소`와 `레포`를 섞어 쓰면 읽는 사람은 둘을 다른 것으로 이해한다.

## 기호와 표기

- 굵게는 놓치면 안 되는 말에만 쓴다.
- `·`, `〃`, `—`, `–`를 쓰지 않는다. 나열은 쉼표나 `와`, `과`로 하고, 문장 사이의 관계는 콜론이나 접속사로 나타낸다.
- `--`는 명령줄 옵션에만 쓴다.
- 경로, 명령, 설정 키, 값, 식별자는 백틱으로 감싼다.
- 조사는 영문, 숫자, 백틱 뒤에서도 띄우지 않고 붙인다(`AGENTS.md를`).
- 저장소 파일은 저장소 루트 기준 경로로 쓴다(`scripts/doc-index.sh`). 홈 디렉터리 아래는 `~/`로, Windows에만 있는 위치는 `%APPDATA%`나 `%LOCALAPPDATA%`로 시작한다.
- 운영체제는 Windows, macOS, Linux 순서로 나열한다.
- 날짜는 `YYYY-MM-DD`로, 시각은 시간대 오프셋을 붙인 ISO 8601(`2026-11-08T09:00:00+09:00`)로 쓴다.
- 목록 기호는 `-`를 쓴다. `scripts/doc-index.sh`가 만드는 `index.md`만 OKF 형식에 따라 `*`를 쓴다.

## 링크

- 저장소 안의 문서는 상대 경로로 링크한다. OKF는 `/`로 시작하는 경로도 허용하지만, GitHub는 그 경로를 저장소 루트에서 찾으므로 `docs/` 안의 링크가 깨진다.
- 절을 가리킬 때는 절 제목을 링크 텍스트로 쓴다(`[링크](writing-style.md#링크)`). anchor가 깨져도 링크 텍스트로 절을 찾을 수 있다.
- 외부 링크는 `[이름](URL)`로 쓴다.

## 코드 주석

- 주석에는 코드만 보고는 알 수 없는 이유를 쓰고, 코드가 하는 일을 되풀이하지 않는다.
- 우회 코드의 주석에는 증상과 원인을 쓴다. 원인이 사라졌을 때 이 주석을 보고 우회 코드를 지울지 판단한다.
  `# Windows는 실행 비트를 기록하지 못한다. 그대로 두면 다른 운영체제에서 hook이 실행되지 않으므로 git 인덱스에 직접 기록한다.`

## 커밋 메시지

커밋 메시지는 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/)을 따른다.

```text
fix(scaffold): 심링크가 있는 경로에는 쓰지 않음

심링크를 따라가면 대상 저장소 밖에 있는 파일을 덮어쓸 수 있습니다.
```

- `type`과 `scope`는 도구가 읽는 식별자이므로 `feat`, `fix(scaffold)`처럼 영어로 쓴다.
- 제목의 설명에는 무엇을 바꿨는지 한 줄로 쓴다. 한국어 제목의 어미는 [문체](#문체)를 따른다.
- 본문에는 왜 바꿨는지 쓴다. 무엇을 바꿨는지는 diff가 보여 준다.
- PR 제목도 커밋 제목과 같은 형식으로 쓴다. squash 병합에서는 PR 제목이 기본 브랜치에 남는 커밋의 제목이 될 수 있다.

## 규칙 문서

front matter의 `type`이 `Standard`인 문서는 다음을 지킨다.

- 규칙에 없는 상황을 판단하는 데 이유가 필요하면 규칙과 함께 이유를 쓴다. 이유가 길면 [결정 기록](decisions.md)으로 옮기고 링크한다.
- 규칙과 함께 바꿔야 하는 파일은 `함께 고칠 곳` 절에 표로 쓴다.
- 규칙을 어디서 확인하는지(CI, 스크립트, 리뷰)는 `검사` 절에 쓴다. `검사` 다음에는 `같이 보기`만 온다.

## 검사

자동 검사는 없다. 리뷰에서 확인한다.
